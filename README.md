## Problem Summary

The Ivy Homes property API (`https://solve.ivy.homes`) is fully functional and honest. However, its **documentation was auto-generated by an AI from an old changelog and shipped without review**. As a result:

- Some documented endpoints **do not exist** (404).
- Some parameters are **silently ignored** by the server.
- Some fields use **different units** than what the docs claim.
- Some documented behaviors are **outright false**.

The task was to:
1. Reverse-engineer the real API behavior by probing it directly.
2. Answer 10 analytical questions about the dataset, accounting for corrupt data, fake listings, and unit bugs.
3. Catalog every discrepancy between the docs and reality as structured `findings`.
4. Build a frontend that **actually works** by compensating for the lies.

## Methodology — How I Found the Lies

I deliberately **did not trust the documentation**. Instead, I treated the API as a black box and reverse-engineered it in 3 phases:

### Phase 1: Probe & Extract (Data Dump)

Before writing any frontend code, I wrote `dump_data.py` to systematically extract the entire dataset. During extraction, I discovered the first set of lies:

| What I tried (following docs) | What actually happened | Action taken |
|------|------|------|
| `GET /v1/listings?api_key=...` | `401 Unauthorized` | Switched to `X-API-Key` header → worked |
| `?page=2` for pagination | Returned page 1 data again | Switched to `?offset=50` → worked |
| `?limit=200` | Server capped at 50 records | Paginated in batches of 50 |
| `GET /v1/favourites` | `404 Not Found` | Implemented favourites in localStorage |
| `GET /v1/analytics/summary` | `404 Not Found` | Built analytics from raw data |

I fetched **every record** across all endpoints (4,300 listings, 1,740 rentals, 480 projects) and saved them locally as JSON files. This was critical because it let me do all analysis offline without hitting rate limits.

### Phase 2: Offline Forensics (Data Analysis)

With the full dataset downloaded, I used `pandas` to systematically hunt for anomalies:

1. **Unit Analysis (`analyze_units.py`):** Grouped `carpet_area` by `website` and computed mean values. The `magichomes` website showed an average of 711, while all others were ~1,130. Cross-referencing with BHK counts proved that magichomes areas under 300 were in **square meters**, not square feet.

2. **Fraud Detection (`find_fakes.py`):** Grouped `posted_by_contact` against `posted_by_name`. Found 12 phone numbers that posted under 3–6 different alias names — a classic lead-generation scam pattern. These 282 listings were flagged as fake.

3. **Corruption Detection:** Filtered for physically impossible values: negative prices, `carpet_area > super_built_up_area`, `floor > total_floors`, and coordinates outside the Bangalore bounding box (lat 12–14, lon 77–78). Found 203 corrupt records.

### Phase 3: Structured Findings

Compiled all 14 discrepancies into the `findings` array in `submission.json`, each with the endpoint, category, documented vs actual behavior, how it was discovered, its impact, and evidence IDs.

## Negative Hypotheses — Things I Tested That Turned Out Fine

A crucial part of the investigation was testing hypotheses that could have been lies but weren't. This is important because **false positives would corrupt the answers just as badly as missed lies**.

### ❌ Hypothesis 1: "Rental prices are annual, not monthly"
- **Test:** Computed descriptive statistics across all 1,740 rental records.
- **Result:** Min ₹7,500, Mean ₹35,000, Max ₹91,000. These are perfectly reasonable monthly rents for Bangalore apartments. If they were annual, they'd be absurdly low (₹625/month for a 1 BHK).
- **Verdict:** Prices are monthly as documented. ✅

### ❌ Hypothesis 2: "GPS coordinates are randomized or globally scattered"
- **Test:** Checked latitude/longitude bounds against the Bangalore metro area (lat 12.8–13.1, lon 77.5–77.7).
- **Result:** 4,294 out of 4,300 listings have valid Bangalore coordinates. Only 6 are outliers (flagged as corrupt).
- **Verdict:** Coordinates are real and accurate. ✅

### ❌ Hypothesis 3: "Listing descriptions contain hidden phone numbers or spam"
- **Test:** Regex-searched all 4,300 descriptions for patterns like `+91XXXXXXXXXX`, `call`, `contact`, `enquire`.
- **Result:** Zero matches. All descriptions are clean, natural-language property descriptions.
- **Verdict:** Descriptions are genuine. ✅

### ❌ Hypothesis 4: "The API returns different data for the same request (non-deterministic)"
- **Test:** Hit `GET /v1/listings?offset=0` three times and compared the response bodies.
- **Result:** Byte-identical responses every time. The API is fully deterministic.
- **Verdict:** API is stable and reproducible. ✅

### ❌ Hypothesis 5: "Non-magichomes websites also have area unit bugs"
- **Test:** Computed average carpet area per website: `100acres` (1,135), `dwelling` (1,120), `squarelane` (1,123), `zerobroker` (1,138).
- **Result:** All four non-magichomes websites have nearly identical averages (~1,130 sqft), which is the expected mean for a mix of 1–5 BHK apartments.
- **Verdict:** Only `magichomes` has the sqm bug. ✅

### ❌ Hypothesis 6: "Filter query parameters actually work"
- **Test:** Sent `GET /v1/listings?furnishing=MARTIAN_FURNITURE` (a completely fake value).
- **Result:** API returned `200 OK` with 50 normal listings. It silently ignores all filter parameters.
- **Verdict:** Filters are broken server-side; must be done client-side. ✅ (This confirmed a real lie.)

## Frontend Architecture & Design Decisions

The frontend was designed with one principle: **never display data that hasn't been corrected for known lies**.

### Key Compensations Built Into the UI

| Lie | How the Frontend Compensates |
|-----|-----|
| Auth requires `X-API-Key` header | `api.ts` injects the header automatically on every request |
| Token expires in 15 min, not 24 hr | `AuthContext` catches 401 errors and forces re-login |
| Pagination uses `offset`, not `page` | All data fetching loops use `offset` parameter |
| Filters are silently ignored | Full client-side filtering (locality, BHK, price, furnishing) |
| `/v1/favourites` is 404 | `useFavourites` hook stores saved listings in `localStorage` |
| `/v1/analytics/summary` is 404 | Insights page computes all analytics from raw listing data |
| Inactive listings are returned | Listings feed filters out `is_live === false` before rendering |
| `magichomes` areas are in sq meters | `getNormalizedArea()` multiplies by 10.7639 before display |
| Project prices are in Lakhs/Crores | Projects page formats with proper unit labels |
| Rental deposits sometimes in "months" | Rentals page multiplies deposits < 20 by the monthly rent |

### Pages

1. **`/` — Listings Feed:** Paginated grid with client-side filters. Shows only live listings.
2. **`/listings/[id]` — Detail Page:** Full property info, seller contact, similar properties.
3. **`/rentals` — Rental Listings:** Corrected deposit display.
4. **`/projects` — Builder Projects:** Prices displayed in human-readable Lakhs/Crores format.
5. **`/saved` — Favourites:** Client-side localStorage-based saved properties.
6. **`/insights` — Analytics Dashboard:** Charts showing data integrity issues, fake listing distribution, and the magichomes unit bug. Built with Recharts.
